# 5.0.0 Release Planning

**Status:** planning. Not started on this branch. 5.0.0 is a **major version bump** — it is
allowed to break API and drop runtimes.
**Captured:** 2026-11-12.

5.0.0 bundles three independent workstreams plus the version/packaging mechanics. Each can be
built on its own branch and merged; they share only the fact that all are breaking and so must
ride the same major.

1. **Python support change** — drop 3.9 & 3.10, add 3.14 (defer 3.15). *(New here.)*
2. **Assessment-layer getters** — POA&M / AP / AR. *(Implemented + tested on the assessment
   feature branch; merge it.)*
3. **Getter-naming consistency + library-wide provenance migration.** *(Designed on the
   assessment feature branch — see `NAMING_CONSISTENCY_PLAN.md` there.)*

Keep (1) and (2)/(3) independent: they do not depend on each other.

## 1. Python support change — drop 3.9 & 3.10, add 3.14

**Rationale.** Python 3.9 reached upstream end-of-life in **October 2025** and 3.10 in
**October 2026** — both are past security support. 3.14 has been stable since Oct 2025. 3.15
(released Oct 2026) is **deferred** until all dependency wheels (notably PyYAML) are published
for it. New supported range: **3.11 – 3.14**, floor `requires-python = ">=3.11"`.

Also: `actions/setup-python` has no 3.9 build for Ubuntu ≥24.04 (CI runners are now 26.04), so
3.9 CI is only green via an `ubuntu-22.04` pin — dropping 3.9 removes that wart entirely.

### pyproject.toml
```toml
# [project]
requires-python = ">=3.11"          # was ">=3.9"

classifiers = [
    "Programming Language :: Python :: 3",
    "Programming Language :: Python :: 3.11",   # drop 3.9 and 3.10
    "Programming Language :: Python :: 3.12",
    "Programming Language :: Python :: 3.13",
    "Programming Language :: Python :: 3.14",    # add
    ...
]

# [tool.ruff]
target-version = "py311"            # was "py39"

# [tool.ruff.lint]
select = ["E", "F", "W"]            # drop FA102 (+ its comment) — the py39 PEP 604 guard is moot at >=3.11
```

### Checklist
- [ ] **pyproject.toml** — the diff above (`requires-python`, classifiers, ruff `target-version`,
      drop `FA102`).
- [ ] **CLAUDE.md** — update the authoritative mandate `"Python 3.9 - 3.13"` → `"Python 3.11 -
      3.14"`. (Governs all future work; easy to miss.)
- [ ] **`HOLD/ci.yml`** (then redeploy to `.github/workflows/`) — matrix →
      `["3.11", "3.12", "3.13", "3.14"]`; **remove** the `include:` / `os: ubuntu-22.04` pin +
      comment added for the 3.9 patch (all legs run on `ubuntu-latest` again). Lint + test jobs.
      Optionally bump `sbom-smoke` / `support-data` from 3.12 → 3.13.
- [ ] **Docs** — README and any page that states the supported Python range; ROADMAP CURRENT.
- [ ] **Wheel sanity** — see §0.

### Optional, unlocked by the floor bump (do deliberately, NOT as part of the bump)
- [ ] With `FA102` gone and floor ≥3.11, drop the `from __future__ import annotations` +
      string-annotation workarounds (`"bool | None"` → `bool | None`, `"list | None"` →
      `list | None`, etc.) and use native PEP 604 unions throughout. This is a large mechanical
      sweep — its own PR, after the version bump is stable.
- [ ] Optionally raise dependency floors onto versions that already dropped 3.9/3.10.

## 2. Assessment-layer getters (POA&M / AP / AR)

**State:** implemented and fully tested on the **assessment feature branch** (then reverted
from the patch branch when we switched off it). 5.0.0 = merge that branch. Design/reference
docs live there: `assessment_getters.md`, `METHOD_PATTERNS.md`, `COVERAGE.html`.

What that branch adds (summary, so this plan stands alone):

- **`POAM.poam_tree`** — a lightweight, UI-oriented cross-reference tree
  (`poam-items` / `observations` / `findings` / `risks`), analog of
  `SSP.implementation_tree` / `Catalog.controls_tree`; rebuilt on validate / mutation.
- **Intra-document getters** on AR + POA&M: `.observation(uuid)`, `.risk(uuid)`,
  `.finding(uuid)` — keyed by uuid; AR annotates the owning `result-uuid`. Each **injects**
  the objects its `related-*` arrays cite (`related-observations`→`observations[]`,
  `related-risks`→`risks[]`), resolves observation `subjects[]` by type, resolves
  `relevant-evidence` fragment hrefs to the back-matter `resource`, and **populates every
  `origins[].actors[]`** in the hierarchy via `.actor()`. A `_seen` path-guard prevents
  cyclic recursion.
- **`POAM.poam_item(uuid)`** — same handling (actors + `findings[]`/`observations[]`/`risks[]`
  injection from `related-findings`/`related-observations`/`related-risks`).
- **`.actor(actors)`** (AR + POA&M) — helper that returns a copy of an `actors[]` array with
  each actor's cited object injected by `type` (`tool`→component, `assessment-platform`→
  `assessment_platform`, `party`→`get_party_by_uuid`).
- **Cross-chain local-definition getters** on AP/AR/POA&M (shared mixin), traversing the
  import chain to the SSP by default (`local_only=True` to stay local), first-found-wins,
  each returned object carrying a **`provenance` = `{uuid, href, imported}`** of its source
  document:
  - `.components()` / `.component(uuid, local_only, include_all)`
  - `.inventory_items()` / `.inventory_item(uuid, local_only, include_all)`
  - `.users()` / `.user(uuid, local_only, include_all)`
  - `.assessment_platforms()` / `.assessment_platform(uuid, local_only, include_all)` (injects
    a `components[]` array from `uses-components`)
  - Singular getters take `include_all=True` → an `additional-versions` array (flattened,
    nearest-first); supersession is **content-preserving** (an SSP-owned component bubbles up
    in its full `SSP.component()` shape, not a sparse local one).
- **`.subjects(subjects)`** (AP/AR/POA&M) — selection-form helper: resolves `include-subjects`
  (and materializes `include-all`) by type, inserting a `title` (name/title, with the
  inventory-item title-fallback prop order), plus `type` + `asset-type` for components.
- **`SSP.components()`** (oscal_implementation) — index shaped like the `components` portion of
  `implementation_tree`; `_build_implementation_tree` refactored to use it (no duplicate code).
- **Base-class scope option** — `get_party_by_uuid` / `get_location_by_uuid` and the plural
  `parties()` / `locations()` gained **`stop_at_ssp`** (confine the cascade to the assessment
  chain + the SSP, never the SSP's own profile/catalog) — the correct scope for assessment
  subjects.
- **Tests** (on the feature branch): `test_assessment_helpers`, `test_poam_tree`,
  `test_assessment_local_definitions`, `test_assessment_crossref_injection`,
  `test_assessment_platforms_actors`, `test_poam_item`, `test_assessment_subjects`.

- [ ] Merge the assessment feature branch into the 5.0.0 line; re-run the full unit suite.
- [ ] Re-apply the assessment docs (`assessment_getters.md`, `METHOD_PATTERNS.md`,
      `COVERAGE.html`) and keep `COVERAGE.html` current.

> Note: the assessment getters already use the short-noun form (`.observation()` etc.) that
> the naming convention below standardizes on — so (2) and (3) are consistent, not conflicting.

## 3. Getter-naming consistency (universal `get_<noun>()`)

Full analysis + decision log on the assessment feature branch: `NAMING_CONSISTENCY_PLAN.md`.
Summary:

- **Direction (Option D):** normalize every **single-object** getter to `get_<noun>()` — add
  `get_` to the short-noun detail getters (`.component(uuid)` → `.get_component(uuid)`), and
  drop the `_by_uuid` / `_by_id` suffix from the verbose resolvers (`.get_party_by_uuid()` →
  `.get_party()`). One rule, obvious at a glance, signals "computed lookup, may return None."
- **Open decisions to settle first:**
  - Do plural/collection getters also take `get_` (`.roles()` → `.get_roles()`)? Current lean:
    **single-object getters only; leave plurals as bare plurals** (they shipped in 4.1.0).
  - Carve-outs that stay outside the rule: `*_content` (`resource_content`, `link_content` —
    they *acquire bytes*, not "get a node") and the `*_tree` view attributes (`controls_tree`,
    `implementation_tree`, `poam_tree`).
  - Key-type disambiguation: dropping `_by_<key>` is fine while each noun has one natural key;
    reintroduce `get_<noun>_by_<key>()` only if a second lookup key is ever needed.
- **Deprecation:** add each old name as a thin forwarding alias emitting
  `DeprecationWarning`; keep both valid through the 4.x line; **remove the old names in 5.0.0**;
  migrate all internal call sites so the library doesn't trip its own warnings.
- **Record** the convention in `METHOD_PATTERNS.md` and annotate the alias pairs in
  `COVERAGE.html`.

## 4. Library-wide provenance migration

Also from `NAMING_CONSISTENCY_PLAN.md` (§5b). Locked representation:
**`provenance = {uuid, href, imported}`** — owning document root uuid, resolved href, and
whether it was reached through an import (`imported` False only for the calling document);
**always present** (no "absence = local" convention).

- **Apply it everywhere content can bubble up via import when not found locally** — the
  base-class cross-reference getters for metadata `roles` / `parties` / `locations` /
  `responsible-parties` / `actions` and back-matter `resources`, not just the assessment layer.
- **Reconcile the three representations that exist today** into one `provenance`:
  - singular `with_source` locator (`object_uuid` + `href`),
  - plural `_collect_in_scope` annotation (`source-document {uuid, href, imported}`),
  - the assessment-layer `provenance {uuid, href, imported}`.
  Promote `provenance` as canonical; keep `source-document` as a deprecated alias through 4.x;
  **add `provenance` to the default (non-`with_source`) singular returns.** That last part is
  the ripple-heavy piece — the singular getters currently return a bare element and feed the
  responsibility-enrichment path and many exact-equality tests — so do it as its own focused
  migration.
- **First-found-wins order = import-array order** (already true: `resolve_imports` builds
  `import_list` in document order and `find_in_import_tree` / `_collect_in_scope` iterate it in
  that order). Pinned by `tests/.../TestMultiImportOrder` on the assessment branch.
- **`additional-versions` is local-definition-only** (components / inventory-items …);
  roles / parties / locations / resources are strictly first-found-wins — no version history.

## 5. Suggested sequencing

1. Land the **Python support change** (§1) first — smallest, unblocks a clean matrix, and is
   independent of the API work.
2. Merge the **assessment getters** (§2).
3. Do the **provenance migration** (§4) — it's the base-class change the assessment layer
   already models, and it touches the enrichment path the getters use.
4. Do the **getter-naming normalization** (§3) last — the widest rename; aliases + internal
   call-site migration; settle the open decisions before starting.
5. Optional modernization sweep (native PEP 604 unions) after the bump is stable (§1 optional).

Each of 1–4 is its own PR into the 5.0.0 integration branch, with the deprecation window
(§3/§4) applied in the 4.x line beforehand where feasible.
